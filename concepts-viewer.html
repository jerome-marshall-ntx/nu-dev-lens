🏗️ Architecture: The Three-Phase System

1

Data Ingestion

Input: JSON file from GitHub
Process: Parse JSON → Insert into PostgreSQL
Output: Database with raw data
💡 Key: One-time bulk load. Design for idempotency (can run multiple times safely).
2

AI Summarization (CLI)

Input: Records with empty summaries
Process: Level 1 → Level 2 → Level 3
Output: All summaries populated
💡 Key: Expensive and slow. Design for resumability (can continue after crash).
3

API Serving + Frontend

Input: User requests
Process: Fast DB reads, stream LLM for chat
Output: Rendered UI with summaries
💡 Key: Fast and cheap. No AI except chat queries.

📊 Data Model: Entity Relationships

📦 Repository

A GitHub repo

"What is this repo about?"

👤 Contributor

A GitHub user

"Who is this person?" (L3)

↓ connected through ↓

🔗 RepositoryWork

Join table with business logic

"What did they do in THIS repo?" (L2)

↓ contains ↓

🎫 Issue

GitHub issue worked on

"What was this issue about?" (L1)

💾 Commit

Code commit made

"What change did this make?" (L1)

🔑 Critical Relationship Understanding

Issues and Commits don't directly belong to Contributors.

They belong to the RepositoryWork (the specific relationship).

This allows the same contributor to have different summaries in different repos.

🤖 AI Processing Pipeline: Dependency Chain

Level 1

Atomic Summaries

Issues: Extract technical facts from raw data → 2-3 sentence summary
Commits: Describe technical change, mention files/functions → 1-2 sentences
Temperature: 0.3 (factual)
Max Tokens: ~100
Parallel? ✅ 8 concurrent workers
→
Level 2

Repository Work Synthesis

Input: All L1 summaries for this RepositoryWork
Task: Identify patterns, group work types, describe focus areas
Temperature: 0.4 (pattern recognition)
Max Tokens: 250
Parallel? ✅ 8 concurrent workers
→
Level 3

Contributor Profile

Input: All L2 summaries across ALL repos
Task: Infer expertise, identify specializations, assess breadth vs depth
Temperature: 0.5 (inferential)
Max Tokens: 350
Parallel? ✅ 8 concurrent workers

⚠️ The Dependency Rule

Level 1 (all done) → Level 2 (all done) → Level 3 (all done)

You cannot start Level 2 until ALL Level 1 is complete. You cannot start Level 3 until ALL Level 2 is complete.

📋 Level 1: Issue & Commit Summaries (Detail)

🎫 Issues System Prompt

"Generate detailed technical summaries of GitHub issues based on raw JSON data. Focus on the specific technical problem, the proposed solution, and any key technical components, features, or modules mentioned. If the issue mentions specific functions, classes, or files, ensure these details are included. Avoid generalizations; stick to technical facts."
Example output:

"Bug fix for null reference in UserAuth module during login"

💾 Commits System Prompt

"Generate detailed technical summaries of GitHub commits based on raw JSON data. Focus on the technical change implemented, primarily using the 'message' field. Describe what code was added, removed, or modified and its specific technical purpose. Explicitly mention names of key functions, classes, methods, or files that were changed."
Example output:

"Fixed null pointer exception in UserAuth by adding validation check"

📋 Level 2: Repository Work Summary (Detail)

🔗 System Prompt

"Summarize a contributor's specific contributions within one particular repository. You will receive Markdown summaries of individual issues and commits. Synthesize these into a coherent paragraph (2-4 sentences). Describe the contributor's primary activities and areas of focus within this specific repository. Identify and group the types of tasks performed. Mention key technical areas or components they worked on."
Example output:

"Focused on backend API bug fixes, particularly in authentication and authorization modules. Contributed to database query optimization and added comprehensive test coverage for user management endpoints."

Business Logic: Groups all atomic summaries by RepositoryWork. Asks LLM to identify patterns and focus areas. Creates a coherent narrative of the contributor's role in that specific repository.

📋 Level 3: Contributor Profile (Detail)

👤 System Prompt

"Create a high-level profile summary for a contributor based on summaries of their work across different repositories. Synthesize these into a coherent paragraph (3-5 sentences) describing the contributor's overall technical profile, recurring themes, and inferred technical skills. Focus on identifying consistent patterns: Does the contributor specialize? What is their apparent primary role? What specific technologies do they engage with? Are their contributions broad or focused? Generalize and infer skills to paint a picture of the contributor as a whole."
Example output:

"This contributor consistently focuses on backend development across multiple projects, demonstrating expertise in Python and Django. They frequently tackle complex bug fixes in API layers and contribute significantly to database schema design and optimization. Their work suggests strong analytical skills and deep understanding of server-side application architecture."

Business Logic: Identifies consistent patterns across ALL repositories. Infers technical skills and specializations. Assesses breadth vs depth of contributions. Creates a holistic professional profile.

⚙️ CLI Tool Architecture

The Tool's Responsibilities

🔌 Connection

Open connection, process items, close cleanly. Handle connection pooling.

📤 Distribution

Find empty summaries, divide among workers (e.g., 8 workers).

📊 Progress

Report every 10% or 100 items. Show elapsed/remaining time.

🛡️ Errors

Rate limits → continue. Timeouts → continue. DB errors → fail fast.

🔄 Resumability

Only process empty summaries. Safe to run multiple times.

💬 Natural Language Query System

1

User Input

"Who's the expert on React components?"

2

Context Assembly

Query database for ALL data. Format into structured prompt with repositories, contributors, work summaries, issues, and commits.

3

LLM Reasoning

The LLM reads the entire knowledge graph, identifies matching contributors, explains reasoning, uses special markup: <contributor id="X">Name</contributor>

4

Streaming Response

Backend streams tokens as they arrive. Frontend renders incrementally. User sees "thinking" in real-time.

5

Frontend Parsing

Detect contributor tags in markdown. Convert to clickable links. Navigate to detail pages.

💡 Key Insight: You're not searching text. You're giving the LLM a structured knowledge base and asking it to reason about it. The summaries make this feasible within token limits.

Why Timestamps?

  • • Track data freshness
  • • Show "last updated" in UI
  • • Enable incremental updates

Why Empty Summaries?

  • • CLI can query WHERE summary IS NULL
  • • Makes resumability trivial
  • • Clear processing state indicator

Why JSON Fields?

  • • Preserve original GitHub data
  • • Allow re-processing
  • • Future enhancements without re-fetch

🔌 API Design

GET /api/data

Returns entire knowledge graph (repositories + contributors with nested data). Frontend loads once on mount, caches in memory. Good for <1000 contributors.

POST /api/chat

Streaming endpoint. Input: user's question. Assembles context + calls LLM + streams response via Server-Sent Events.

GET /api/contributors/:id

Single contributor with all details. Optional if frontend already has cached data from /api/data.

💡 Design Philosophy: Start simple (one big query), optimize later (pagination, filtering) if needed.

🖥️ Frontend State Management

1

On App Mount

Fetch from /api/data → Store in memory (React state/context) → Set loading to false

2

Throughout App

All pages read from in-memory data. No additional API calls. Fast, offline-capable browsing.

3

For Chat

Separate API call to /api/chat with streaming. Independent from cached data.

Why This Works

• Data changes infrequently (only when summaries regenerated)

• Single load + client-side filtering is faster than multiple API calls

• Simplifies code (no loading states on every page)

💰 Cost & Performance

One-Time Costs (Phase 2 - CLI)

Example data: 1000 commits, 500 issues
Total LLM calls: ~1,650 calls
Total tokens: ~1 million
Estimated cost: $0.50-$5
Time: 1-4 hours

Ongoing Costs (Phase 3 - Runtime)

Per chat query: ~10-50k tokens
Cost per query: $0.01-$0.10
Database reads: Negligible
Hosting: Normal web app
💡 Optimization Strategy: Pre-compute everything possible (Phase 2). Serve cached data at runtime (Phase 3). Only use LLM for chat queries.

✅ Final Conceptual Checklist

✓ The three phases are separate systems (ingestion → processing → serving)
✓ Hierarchical summarization builds knowledge bottom-up (atomic → synthesis → profile)
✓ The join table has business logic (RepositoryWork.summary is critical)
✓ Level dependencies prevent parallel processing across levels
✓ CLI tools are separate from the web application
✓ Summaries are pre-computed, not generated on-demand
✓ Chat queries use entire knowledge graph as LLM context
✓ Custom markup creates interactivity in LLM responses
✓ Type safety flows from database schema through the entire stack
✓ Error handling differs between phases (fail fast vs. graceful degradation)
